# Qwen3.6-27B NVFP4 W8 Endpoint Implementation Plan

This temporary plan defines the work required to specify and implement W8 storage for the
`qwen3.6-27b/nvfp4` Text endpoints. It is not an artifact authority and does not change the
currently documented format. Delete it when the work is complete.

## 1. Deliverable and boundaries

The work will make these two tensors `W8G32_F16S` in the 27B NVFP4 weight specification and its
implementation:

| Object | Shape | Planned format |
|---|---:|---|
| `text/token_embedding` | `[248320,5120]` | `W8G32_F16S` |
| `text/output_head` | `[248320,5120]` | `W8G32_F16S` |

The work does not change:

- the `qwen3.6-27b/groupwise-int` weight specification;
- any `qwen3.6-35b-a3b` weight;
- `text/draft_head`, Vision patch projection, or other tensor formats;
- the artifact identity, recipe id, filename, generic container, or public Engine route;
- Qwen3.6 family scheduling, state transactions, workspace composition, or graph frontier.

The exact 27B package will own the profile-specific endpoint binding. The family runtime will
continue to call the same Embedding and Linear Ops without artifact-identity or weight-profile
branches.

## 2. Execution order

Each stage has its own deliverable and stop condition. Stage 1 is the only active stage in the
current execution. It does not modify an artifact authority, converter, target binder, generated
artifact, Embedding Op, model card, README, or performance reference. Stop after its production
W8 Linear route and focused verification are complete.

### Stage 1: implement and tune the W8 Linear Op

Complete the W8 Linear work as an independent operator deliverable:

1. build and sweep reusable W8 Linear kernels for `[N,K] = [248320,5120]` as specified below;
2. retain only the winning production kernel instantiations and register the geometry in W8
   dispatch;
3. qualify the public Linear route against the independent oracle at `T=1`, `T=6`, `T=16`,
   `T=32`, and the selected route boundaries;
4. stop without executing any later artifact or endpoint-integration stage.

#### Stage 1.1: benchmark ownership and experiment lifetime

`bench/ops/linear_bench.cu` is the benchmark for the public Linear contract. It may include and
call only the public Linear interface; it must not expose private launch functions, candidate
routes, or route-selection flags. It may measure the 27B W8 geometry after production dispatch is
registered, but that measurement must enter through `ninfer::ops::linear`.

Development-time route selection instead uses a temporary
`bench/ops/w8_linear_tuning_bench.cu` and a temporary build target. That executable may directly
instantiate private kernel templates and compare candidate schedules. It owns all candidate names,
direct-launch adapters, sweep tables, and experimental output. It must:

- construct the exact `W8G32_F16S` geometry and compare cold-cache launches;
- run the independent numerical oracle before timing each admitted candidate;
- sweep compile-time schedule instantiations directly, without adding them to W8 production
  dispatch;
- support focused Nsight Compute launches for a finalist when timing alone is inconclusive.

After selection, promote only the reusable kernel core and compile-time schedule instantiations
used by production. Delete the temporary benchmark, its build target, candidate-only aliases and
launch adapters, and any experiment-only source. The final W8 launch header and dispatcher must
contain no candidate catalogue or development route.

#### Stage 1.2: performance model

For `[N,K] = [248320,5120]`, one W8 weight pass consists of:

| Payload | Bytes |
|---|---:|
| signed W8 codes | 1,271,398,400 |
| FP16 G32 scales | 79,462,400 |
| total weights | 1,350,860,800 |
| BF16 input plus output per token | 506,880 |

At the measured RTX 5090 sustained-read reference of 1,674.5 GB/s, the one-pass lower bound is
approximately 807 us at `T=1` and 812 us at `T=16`. Reading the weight payload twice raises that
bound to approximately 1.61 ms before activation and output traffic.

Small T does not by itself rule out MMA. The exact logical work at `T=16` is 40.7 GFLOP, whose
BF16 Tensor Core floor is far below the one-pass memory floor. A generic MMA tile that physically
computes 64 or 128 tokens would perform 162.7 or 325.5 GFLOP, giving approximate compute floors of
777 us or 1.55 ms. Therefore MMA is a credible small-T route only with an 8- or 16-token physical
tile and exact compile-time active-token masking. The sweep must not reuse a 64/128-token generic
tile as evidence against small-T MMA.

The large output dimension supplies thousands of independent M tiles, so K splitting is not
needed to create global parallelism. It remains a valid per-CTA schedule: multiple warps can
cooperatively stage a 16-row weight tile, evaluate disjoint K slices, and reduce FP32 partials while
every persistent code and scale byte is still read once. The sweep therefore compares M-parallel
and 4/8-way K-split schedules on their measured load efficiency, latency hiding, and reduction
cost rather than choosing from global parallelism alone.

#### Stage 1.3: reusable compile-time kernel model

The retained exact-small-T W8 kernel follows the separation used by the BF16 and NVFP4 Linear
implementations:

```cpp
template <std::int32_t OutputRows, std::int32_t InputRows>
struct W8LinearGeometry;

template <int KWarps, int TileTokens, int MinBlocksPerSm, /* cache and scale policies */>
struct W8SmallTMmaSchedule;

template <class Geometry, int ActiveTokens, class Schedule, class OutputPolicy>
__global__ void w8_small_t_mma_kernel(...);
```

`W8LinearGeometry` owns compile-time output and input dimensions, G32 group count, code-row bytes,
and scale-row bytes. It requires a positive shape and an input dimension divisible by 32. The
registered 27B endpoint is an alias of `W8LinearGeometry<248320,5120>` at the dispatch boundary;
the kernel name and body contain neither those dimensions nor a model or tensor identity. After
the host launcher validates the public tensors, the core receives pointers and `OutputPolicy`;
output rows, input rows, strides, group counts, and loop bounds come from `Geometry`, not runtime
`n`, `k`, or `t` arguments.

`ActiveTokens` is exact and compile-time. The production launcher generates a function table for
`T=1..32`, as the BF16 and NVFP4 small-T launchers do. The kernel has no runtime loop over possible
T values and stores only the active columns. A schedule may use a physical MMA token tile of 8,
16, 24, or 32, but inactive fragments and stores are resolved from `ActiveTokens` at compile time.

The retained schedule type owns only code-generation choices: K-split warps, physical token tile,
scale access, code and activation cache policies, and launch bounds.

The schedule derives thread count, warp layout, shared-memory capacity, and tile counts and rejects
invalid combinations with `static_assert`. A registered geometry selects a compatible schedule;
adding another shape means defining another `W8LinearGeometry` alias and measured production
selector, not copying or renaming a kernel. `OutputPolicy` owns row/token addressing and BF16
storage so the computation body remains reusable by an existing semantically compatible W8 Op
without introducing a packed intermediate.

The final configuration contains production selectors, analogous to
`Bf16LinearSmallTProductionSchedule` and `Nvfp4LinearSmallTProductionSchedule`. There is one
selected schedule and kernel family for each admitted `(Geometry, ActiveTokens)` instantiation.
If one family wins the whole band, the selector is uniform. If the measured crossover is inside
the exact-T band, the selector records only the winner on each side; it does not preserve losing
routes.

#### Stage 1.4: retained computation design

The selected small-T MMA computation is a reusable K-split schedule:

1. a CTA stages a 16-row tile of W8 codes, its G32 FP16 scales, and the active columns of a
   compile-time BF16 activation tile;
2. codes are sign-extended, multiplied by their stored scale, and converted to the BF16 shared
   operand expected by `m16n8k16`;
3. eight warps evaluate disjoint 64-wide K slices with FP32 Tensor Core accumulation;
4. the CTA reduces the eight FP32 partial tiles in shared memory;
5. only `ActiveTokens` columns are converted to BF16 and stored through `OutputPolicy`.

One G32 scale feeds the two consecutive K=16 MMA steps belonging to that group. The launch grid
has `OutputRows / 16` M blocks and one token block for the exact-T specialization. The code and
scale payload for an output row is traversed once per launch; there is no cross-CTA workspace or
reduction. Shared storage, K-split count, token tile, scale access, cache policy, and launch bounds
are compile-time schedule values. The independent oracle decodes signed codes with the stored FP16
scale and accumulates the logical formula in FP32/FP64; candidates are each checked against that
oracle rather than against one another.

#### Stage 1.5: sweep and selection

The temporary benchmark screened the existing SIMT and generic MMA controls against compile-time
exact-T schedules. The exact-T sweep covered four and eight K-split warps, 8- and 16-token
physical tiles, direct and shared scale access, launch bounds, and cache policies. Only after that
family won through `T=16` was its smallest enclosing physical tile extended to 24 and 32 tokens.
The staged sweep measured `T={1,2,4,6,8,9,12,16}` first, every `T=1..16` for finalists, and then
the exact-T/generic crossover through `T=65`.

Use Nsight Compute only when finalists cannot be separated by stable direct measurements or a
material shortfall remains unexplained. The focused points are `T=1`, `T=6`, `T=9`, and `T=16`;
the relevant evidence is DRAM bytes and throughput, Tensor Core utilization where applicable,
registers, spills, achieved occupancy, and dominant warp stalls.

The retained production selection is:

| T range | Route |
|---|---|
| `1..32` | exact-T `W8SmallTMmaSchedule`, eight K-split warps, 16 output rows per CTA |
| `33..64` | existing 64-column generic MMA |
| `>=65` | existing 128-column generic MMA |

For the exact-T route, the physical tile is the smallest of 8, 16, 24, or 32 columns that contains
`ActiveTokens`; scales are read directly for `T<=4` and staged in shared memory for `T>=5`.
`W8LinearSmallTProductionSchedule<Geometry, ActiveTokens>` records these choices with two
blocks-per-SM launch bounds. No losing candidate launcher or schedule catalogue remains in
production.

Production integration:

- instantiates the selected geometry/schedule combinations in ordinary W8 source files;
- exposes one geometry-level small-T launcher, with exact-T function pointers generated at compile
  time;
- routes `[248320,5120]` through one exact-T launcher table for `T=1..32`;
- routes `T=33..64` through the measured 64-column generic MMA and `T>=65` through the measured
  128-column generic MMA;
- measures the final route again through the public Linear benchmark.

On RTX 5090 with cold-cache public Linear measurements (`warmup=3`, `repeat=15`), the selected route
measured 782.016 us at `T=1`, 791.680 us at `T=6`, 793.184 us at `T=16`, and 990.496 us at
`T=32`. The generic boundary routes measured 1293.600 us at `T=33`, 1320.160 us at `T=64`, and
1768.288 us at `T=65`.

Stage 1 stop condition: the public Linear route passes the focused oracle cases, including the
`T=32/33` and `T=64/65` boundaries; the temporary benchmark, temporary target, and losing
candidate-only routes are removed. Do not continue to Stage 2 in this execution.

Update the artifact reference with generated facts where applicable, then update the project
README, NVFP4 model card, and performance reference with the actual byte count, SHA-256, accuracy,

## 3. Completion

The work is complete when the 27B NVFP4 specification and implementation assign W8 to both
endpoints, the tuned W8 routes serve the complete product T domain, the other weight specifications
remain unchanged, generated public metadata describes the produced artifact, and this temporary
plan has been deleted.
