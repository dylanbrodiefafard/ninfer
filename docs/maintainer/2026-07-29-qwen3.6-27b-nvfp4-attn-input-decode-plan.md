# Qwen3.6-27B NVFP4 Attention Input Decode 实施方案

## 1. 状态与目标

本文是 A1 `attn_input_proj` 的 NVFP4 `T=1` decode 临时实施方案。它记录本阶段的固定语义
边界、最小可运行 kernel、实测候选和完成条件。kernel 组织、staging、线程映射和数值指令
路径均是可被 correctness、benchmark 或 profiler 证据推翻的实现假设，不是产品合同。

本阶段完成两个 `T=1` production route：

```text
Linear:
    x      BF16  [5120,1]
    weight NVFP4 [14336,5120]
    out    BF16  [14336,1]

AttnInputProj:
    x      BF16  [5120,1]
    weight NVFP4 [14336,5120]
    q      BF16  [6144,1]
    gate   BF16  [6144,1]
    k      BF16  [1024,1]
    v      BF16  [1024,1]
```

pure Linear route 是永久能力和永久 benchmark point，不是临时候选入口；它不因此成为
NVFP4 artifact 的独立消费项。artifact attention parent 仍由 `attn_input_proj` 消费。

`T=1` 只是本阶段完成的 private execution frontier。Text `T` 的语义域仍是每个正值，A1
在 Small-T 和 prefill route 完成前保持 partial progress，不把 decode 写成新的语义变体、
public API 或完整 registration。

稳定的 Op 合同、benchmark 命令和 A1 进度分别并回现有 active references；本方案保留到
本阶段验收结束，随后删除。

## 2. 固定边界

### 2.1 数学与格式

public activation 和输出均为 BF16。A16 decode 不量化 activation。persistent weight 的
逻辑值为：

```text
W[n,k] =
    decode_e2m1(code[n,k])
    * decode_e4m3fn(scale[n,floor(k/16)])
    / weight_scale_divisor
```

每个完整 dot product 与现有 A16 criterion 比较。实现可以选择自然的 conversion、
coefficient、FMA association、reduction 和 staging 路径；这些均不是 oracle。

`weight_scale_divisor` 和 `input_scale_divisor` 都必须有限且严格大于零。A16 数学公式不包含
`input_scale_divisor`，kernel 不需要接收它。测试使用合法的非单位 `input_scale_divisor`
执行正常 oracle case，不另建 bitwise-invariance 或特殊浮点值矩阵。

不预先物化或缓存完整反量化权重，不增加 workspace，不执行隐藏 device allocation。

### 2.2 Attention 输出映射

完整 parent 的物理行顺序为：

| Parent row | 语义 | 输出 |
|---:|---|---|
| `[0,6144)` | query | `q[0:6144]` |
| `[6144,7168)` | key | `k[0:1024]` |
| `[7168,13312)` | output gate | `gate[0:6144]` |
| `[13312,14336)` | value | `v[0:1024]` |

不存在 observable packed output。kernel 直接写四个 caller-owned allocation。

### 2.3 所有权

矩阵计算主体属于 `src/ops/linear/nvfp4/`。Linear 和 Attention 各自在自己的 production
translation unit 定义一个按值传递的小型 output object：

```text
output.store(parent_row, bf16_value)
```

Linear object 写连续 `out`。Attention object 根据 parent row 写 Q/K/Gate/V。该模式与现有
BF16 decode 一致，不增加 `Epilogue::Params`、runtime function object 或 packed scatter。

Attention 可以实例化 Linear-owned kernel body，但不调用 public `linear()`，不依赖 Linear
dispatch，也不复制计算主体。Attention row seam 的 static assertions 属于 Attention TU，
不进入通用 Linear kernel 条件。

每次 public 调用提交一个 kernel launch并使用零 workspace。这是本阶段明确的实现边界，
不是 public Op 合同中的 backend 承诺。

### 2.4 排除项

本工作不修改或接入：

- Engine、Program、family schedule、CUDA Graph 或 runtime；
- `src/targets/**`、binder、LoadedModel 或 artifact materialization；
- CLI、serving、workspace planning；
- Small-T、prefill、A4 activation quantization或其他 NVFP4 semantic Ops；
- Q4/Q5/Q6/W8/BF16 kernel 的重构或重新调优。

## 3. Host admission

### 3.1 Finite dispatch

`linear.cpp` 的 `QType::NVFP4` 分支进入独立 NVFP4 dispatch。当前 route 只接受：

```text
N = 14336
K = 5120
T = 1
policy = LinearPolicy::A16Only
```

single-parent `attn_input_proj` 按 qtype 分类现有 BF16、W8 与新 NVFP4 parent；NVFP4 route
接受相同 `N/K/T`。dispatch 不读取 target key、layer role 或 artifact object name。

public contract 只登记 NVFP4 format、exact `N/K` 和 A16 profile，并将 `T=1` 描述为当前
private implementation frontier，而不是 Text token extent 的语义上限。

### 3.2 NVFP4 weight facts

admission 验证执行实际依赖的完整-parent事实：

- `QType::NVFP4`、`BlockScaleK16M128x4`、`FP8_E4M3FN`；
- rank two，`n/k` 与前两个 logical/padded extents 自洽；
- `group_size == group == 16`；
- `N % 128 == 0`、`K % 64 == 0`；
- code/scale plane 非空且满足 kernel vector alignment；
- `qhigh == nullptr`、`high_plane_bytes == 0`；
- 由实际 `N/K` 推导出的 scale-plane offset 和所需 payload capacity 合法；
- 两个 divisor 有限且严格大于零。

不得写死当前 shape 的 code-plane byte constant。format geometry 从实际 `N/K` 计算，
exact route shape 由 finite dispatch 独立决定。不得扩展成设备内容扫描、逐字段防御框架或
artifact provenance 验证。

non-alias 是已有 Linear/Attention contract 的 caller precondition。本任务不增加
NVFP4-only pointer-range rejection；kernel 与其他类型一样可以根据该 precondition 使用
`__restrict__`。

## 4. 最小 qualification

### 4.1 Oracle

复用 `tests/ops/quantized_weight.h` 的独立 NVFP4 fixture：

- fixture 生成完整 E2M1 code、swizzled E4M3FN scale 和非单位合法 divisor；
- fixture 独立 materialize 逻辑 FP32 weight；
- activation 先舍入为 represented BF16；
- naive FP64 accumulation 计算完整 dot product。

production codec、GPU kernel或另一条实现路径不得成为 oracle。

### 4.2 Linear

新增一个 `[14336,5120], T=1` case，调用 policy-bearing public form：

```text
linear(x, weight, out, LinearPolicy::A16Only, stream)
```

验证：

- 完整 `14336` 行与独立 oracle；
- 所有输出有限且已写入；
- output guards；
- activation 与完整 persistent payload 不变。

不为同一 qtype 重复执行 convenience overload；该通用转发已经由现有 Linear suite 覆盖。
不增加 malformed metadata、alias、private selector 或 `d_x` bitwise tests。

### 4.3 Attention

在现有 `attn_input_proj` qualification 中增加一个 single-parent NVFP4 `T=1` case：

- 四个输出分别与对应 parent row 的同一独立 oracle比较；
- 四个 allocation 完整写入且 guard 保持；
- Q/K/Gate/V 不交换；
- activation 与完整 parent payload 不变。

保留现有 Q4/Q5、W8 和 BF16 cases。只运行受新 dispatch 分支影响的现有回归。

## 5. Permanent benchmark 基建

### 5.1 Weight fixture

Linear 和 input-projection benchmark 各自复用 benchmark-owned NVFP4 device fixture。fixture：

- 分配完整 code/scale/divisor payload；
- 在 timed region 外初始化合法 E2M1、非负有限 E4M3FN、非单位正 divisor 和 `Weight`
  metadata；
- 不读取 checkpoint 或 `.ninfer`；
- traffic accounting 只计 kernel 实际读取的 code、scale、activation 和输出。

### 5.2 Public measurements

pure Linear：

```bash
./build/bench/ninfer_linear_bench \
  --qtype nvfp4 --policy a16 \
  --n 14336 --k 5120 --t 1
```

Attention：

```bash
./build/bench/ninfer_input_proj_bench \
  --op attention --weight-type nvfp4 --t-sweep 1
```

普通 timing、CSV 和 `--profile` 都调用 public production Op。NVFP4 point 不加入
`qwen3_6_27b` pure Linear suite。两个永久 benchmark 不保存 candidate forcing、kernel
名称或一份重复 selector。

## 6. Kernel seed

### 6.1 设计原则

`[14336,5120,1]` 的 code plane 约 35 MiB，属于 cold decode memory workload。seed 优先：

- 单遍读取 code；
- swizzle-aware、coalesced 读取 scale；
- direct activation；
- 无 decoded-weight workspace；
- 一次 warp reduction 和一次最终 BF16 store。

Tensor Core 不进入初始候选。只有 SIMT 实测显示 conversion/math 明确限制、memory traffic
明显低于可达到水平时，才重新评估。

### 6.2 Swizzle-aware row/scale mapping

scale layout 对同一 `row % 32` 的四个 quartile rows：

```text
r, r + 32, r + 64, r + 96
```

存放连续的四行 × 四个 K16 scale bytes。CTA 以 quartet 顺序分配 rows，并让相邻 threads
对同一个 K64 tile 合作读取连续 16-byte scale vector。该 mapping 只解决持久 scale 的
coalescing；它不要求 activation 或 decoded coefficient 使用同样的复杂 layout。

### 6.3 Seed scale 与 activation 路径

seed 使用：

- direct BF16 activation loads；
- coalesced scale-vector loads；
- CTA-local natural-row raw E4M3FN bytes；
- hot loop 中每个 K64 subgroup 读取一个 packed scale word，以 warp shuffle 分发；
- hardware E4M3/E2M1 conversion；
- launcher 计算并传入普通 FP32 `1 / d_w`，coefficient 由 decoded scale 相乘得到；
- FP32 FMA accumulators 和 warp reduction。

raw-scale staging 只需要 `RowsPerCta * K/16` bytes 和一次 barrier。seed 不建立 128-entry
normalization table，不 staged 完整 FP32 coefficients，不复制 activation，也不为极端但
产品中不存在的 divisor 值塑造 kernel。

这是最小性能假设，不是预定 winner。

### 6.4 Compile-time schedule

kernel body 形态为：

```text
nvfp4_gemv_kernel<Geometry, Schedule, Output>(
    x, code_plane, scale_plane, inverse_weight_divisor, output)
```

初始 `Schedule` 只包含当前存在真实候选的参数：

- warps per CTA；
- rows per warp；
- values per lane；
- accumulator chains；
- raw-staged或 direct scale access；
- code cache operator；
- launch-bounds hint。

不预先加入 activation staging、prefetch depth、phase rotation或其他只有单一实现的模板
参数。需要比较第二个实现时再增加对应 compile-time fact，候选删除后同时删除失去用途的
参数。

## 7. 调优流程

### 7.1 顺序

1. seed 通过两个 public numerical cases；
2. 用 pure Linear cold-cache benchmark 测量 production baseline；
3. 在临时 candidate harness 中比较少量相邻 schedule；
4. 先决定 scale path，再比较 row ownership、lane granularity 和 accumulator chains；
5. pure Linear winner 原样实例化 Attention output object；
6. 只有 Attention public timing 出现稳定 material regression 时，比较相邻 Attention
   schedule；
7. 写回每个 entry 的唯一 production alias并删除临时候选 harness。

候选参数按实验需要逐步加入，不预先实现 Cartesian product。

### 7.2 测量

沿用现有 benchmark 的 cold-cache timing 和默认 warmup/repeat。先以 median 区分候选；
候选接近、结果可能改变 winner 时才增加重复。min/p95 用于识别不稳定，不设固定的
`5 × 200` 仪式。

Nsight Compute 只用于回答具体未决问题，例如：

- scale traffic 是否因 direct access 放大；
- long-scoreboard 是否解释低 bandwidth；
- conversion 或 shared access 是否成为瓶颈；
- 某候选是否发生影响 latency 的 spill。

不因为候选进入 finalist 就自动收集整套指标。

### 7.3 Winner

winner 必须：

1. 通过 public numerical qualification；
2. 满足 one launch、zero workspace 和完整输出合同；
3. 在重复的 cold-cache public measurement 中具有最低稳定 latency。

register、occupancy、spill 和 traffic 是解释与 tie-break 证据。除非它们违反明确资源边界
或导致可测性能/正确性问题，否则不作为独立淘汰条件。

## 8. 实施结果与完成条件

实现按以下边界落地：

1. 一个共享 kernel body，通过小型 output object分别服务 pure Linear 与 Attention；
2. A16 activation 直接读取，E2M1/E4M3 使用硬件 conversion，scale 以 swizzle-aware
   16-byte transaction 读入 CTA-local raw staging；
3. production schedule 固定为 `8 warps/CTA`、`2 rows/warp`、`16 values/lane`、
   `4 accumulator chains`、default code cache 和 `2 blocks/SM` launch bound；
4. 临时候选入口已删除，permanent benchmark 只调用 public Op。

RTX 5090、CUDA 13.1、cold-cache 测量中，pure Linear 与 Attention 的 200-sample median
均为 `32.000 us`，对应 logical model traffic `1291.5 GB/s`、实测 pure-read ceiling 的
`77.12%`。相邻 row/lane schedule 为 `34–42 us`。raw-staged 与 direct-scale 的普通
median 接近；NCU 单次受控采样分别为 `33.86 us` 与 `35.26 us`，raw-staged 的 achieved
occupancy 也更高（`30.08%` vs `28.72%`），因此保留 raw-staged。accumulator chains 和
code-cache 的相邻候选没有稳定优于当前 alias。

本阶段完成条件：

- public Linear 与 Attention `T=1` route 均通过同一独立数学 oracle；
- Attention 四个 row range 写入正确 allocation；
- 两个 permanent public benchmark 可运行；
- production 只保留一个共享 kernel body和每个 entry 的一个固定 schedule；
- 最终 schedule 有 RTX 5090 cold-cache measurement 支持；
- 工作树不包含 Engine、target、artifact binding、runtime autotune、dummy/reference
  production route 或遗留 candidate forcing；
- A1 明确保持 positive-T contract 下的 decode partial progress。
