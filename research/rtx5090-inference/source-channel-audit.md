## SC02 — Memra: directly relevant engine, but '5090' has a major hardware qualifier

Source: `https://github.com/avifenesh/memra`, inspected commitdba926cdc. Independent Rust host/CUDA AOT engine, `sm_120a`, Qwen3.8-27B and speculative paths. Read README, `docs/models/qwen38-27b.md`, `docs/rigs/rtx-5090.md`, `docs/PERFORMANCE.md`, `docs/DRAFT-REGIME.md`, and selected `crates/memra-engine/src/hybrid.rs`/own-generation rank tool code.

**Hardware correction:** `docs/PERFORMANCE.md:46–82` explicitly identifies the local tracked '5090' boards as **RTX5090 Laptop, GB203,82SM,858GB/s**. Desktop5090 appears separately in historical rented `rig2x5090-serve` receipts. PRO6000 results are separately labeled. Do not treat the model page's '+3.87% local5090 E2E' as desktop5090 evidence.

Current Qwen27B recommendation is a mixed **NVFP4+Q5_K GGUF trunk**, q4 DFlash2 drafter and agentic32K FR-Spec rank map; safetensorsNVFP4 MTP remains another lane. Neither automatically matches the current `.ninfer` artifact. The general optimized draft-head concept already exists here through MTP draft heads and DFlash2 selector codebooks. The incremental alternative is **workload-derived fixed vocabulary trimming**, with admission and distribution-coverage diagnostics, not 'add a faster LM head'.

Source mechanics: `hybrid.rs:3397–3405` stores a draft-to-target token map and distinguishes rows gathered from the target's own output head from an external student's head. `frspec_read_d2t`, `frspec_validate_ranks` and `frspec_gather_trimmed_head` validate/gather the rank artifact. `src/bin/frspec_owngen.rs` generates a corpus using the exact serving model and compares trimmed versus full draft end-to-end performance. `docs/DRAFT-REGIME.md` reports foreign/corpus-mismatched ranks losing about12 acceptance points and raw-versus-chat derivation excluding structural tokens; it records a class-coverage failure where tuning draft depth did not repair the problem. Those are publisher observations, not reproduced here.

Useful implication: test any alternative proposer on the actual coding/prose/tool distribution and judge verified tokens per whole round, including correction, rather than vocabulary-byte reduction alone. Trimming proposals can remain target-preserving with a correct acceptance law; it is not permission to trim the target distribution. The new rank/draft artifact would need explicit artifact admission and current sampler qualification. Memra's own older prefill board reports deficits versus llama.cpp, another reason not to rank from selected decode wins.

**Extraction constraint:** inspected LICENSE is **FSL-1.1-ALv2**, including a competing-use limitation before its future-license conversion. It is not presently the same permissive license as NInfer. Treat algorithms/papers as research leads; do not assume direct code reuse under Apache-2.0. This report copied no implementation.

## SC03 — xinfer and Fracture: real engines with limited comparative relevance

`https://github.com/guoqingbao/xinfer`, b88c153, MIT metadata. Read English/Chinese README, Cargo manifest and model/runtime source layout. Rust implementation uses pinned **Candle fork** and **attention.rs** plus selectable FlashInfer/FlashAttention/CUTLASS; 'no PyTorch/Python runtime' does not mean all operators were independently written in this repository. Qwen hybrid/dense/MoE, MTP/DFlash2, graphs and Turbo4 KV are supported claims. Explicit5090 rows are Qwen3-30B-A3B NVFP4 **197.29tok/s** and Gemma4-26B-A4B NVFP4 **137.23tok/s**. The27B58tok/s Q4/IQ4 row lacks the same explicit5090 qualification;27BFP8 row is Hopper. Thus no matched27B-NVFP4 speed claim. Theoretical context-capacity tables do not prove admitted long-context quality or latency. Disposition: add landscape coverage; existing local features and lower-bit KV category already covered; no new qualified high-priority kernel delta from this screen.

`https://github.com/nickw409/Fracture`,0d3ff26. README and component layout show a Rust backend abstraction with CUDA/cuBLAS, Llama3.1-8B and heterogeneous5090+3090 pipeline execution. Distributed failover and multi-machine scheduling are outside current product scope. Its TurboQuant K4/V2 attention is a further low-bit KV implementation, but the displayed compression comparison is **RTX3090**, with cosine/greedy checks rather than currentQwen27B long-context quality. It explicitly uses MSE-only rotation/quantization, omitting the paper's QJL correction. No current5090 throughput superiority inferred. Screened, not a complete numerical audit.

## SC04 — remesis nondefault copy-draft branch closes a genuine missed avenue

Source `https://github.com/remesis/ninfer/tree/add/ngram-mod`, commit17605b0d5b1d558b27e50a67b6aee719ffb409aa; primary discussion `https://github.com/Neroued/ninfer/issues/234`; evidence release `https://github.com/remesis/ninfer/releases/tag/ngram-mod-evidence-20260912`. The previous default-branch screen did not establish novelty; this **nondefault branch does**. Apache-2.0 NInfer lineage. Inspected108-file diff summary, `docs/ngram.md`, proposer/index source, sampler contract and acceptance kernel, rather than merely branch metadata.

Up to63 CPU-proposed tokens alongside MTP/DFlash/DFlash2, exact-checked16/8/4-token position lookup, fallback on weak matches, **C1-only admission**. Proposal-only de-numbered tool sources preserve original target text, positions and prefix identity. A bounded RAM archive retains immutable source tokens across conversation compaction; it **does not restore omitted context, KV, or model knowledge**. Cancellation/failure discards the overlay; fork/reset and published generations control retained sources. It is separate from current KV prefix retention and durable Responses history.

Retention additionally separates request acceptance randomness from previously generated retained sources by mixing fresh request entropy into the supplied seed. The effective seed is reported; same user seed alone no longer reproduces an archived conversation. This semantic change must be deliberate if ever adopted. Defaults described are roughly36MiB live index plus128MiB/session and512MiB total archives; wide verification increases device workspace and graph/replay cost.

Primary issue reports controlled byte-exact27B copy-span means: MTP 292→1408 tok/s, DFlash2 286→1521, **4.82x/5.35x**. Those means cover four raw/line-numbered,cold/cached cases, deterministicK5/NG63/NVFP4KV, and explicitly belong to a **pre-v3 evidence revision**, not the later rebased branch or current checkout. Four preselected old-style sampled/thinking pairs report median3.14x whole-request completion; small controlled samples are not a general agent estimate. This positive result can coexist with external normal-agent no-benefit findings: the share of genuinely copyable output determines opportunity.

Actual branch sampler `include/ninfer/ops/sampling.h` restricts top_k to1..20; deterministic copy proposals use q=one-hot and acceptance p(copy), with masked residual correction in `src/ops/kernel/speculative_round.cuh:225+`. DFlash2 feeds one-hot proposals into its sparse verifier. That is not qualification for current p-less/full-support sampling, current grammar, or C2..4. Width-dependent floating-point path changes are explicitly acknowledged in the branch docs; exact-copy benchmark success does not prove all generated trajectories identical.

Issue comments link Wallawalla's historical `windows-ngram-c1-c2`; that named branch is no longer advertised by `ls-remote`. Current Wallawalla master reviewed earlier supplies the multi-request lineage. Do not count remesis and downstream Wallawalla as independent implementations or replicate their speed claims across branches.

## SC05 — Other selected branch discoveries: useful negative results and conditional mask optimization

**q27 adaptive suffix width:** `https://github.com/signalnine/q27/tree/adaptive-suffix-width`, head9cf9654. Inspected commits6bf1815 and51c54d4. The original context-length-based W12/W16 gate claimed16% echo gain; a subsequent exact-file re-emission test exposed width-dependent output divergence and content-dependent speed signs. Replacement uses EMA of actual narrow-cap saturation with0.50/0.30 hysteresis, starting narrow; reported saturating echo735vs617tok/s(+19%) with matching output, while non-saturating file traffic remains narrow. The author correctly retracts blanket byte-identical width claims. **Saturation is a useful policy signal, not a mathematical guarantee against future near-tie divergence.** Current NInfer adaptive neural drafting already exists; this only concerns optional wide copy verification if that feature is adopted. No guaranteed ordinary-agent improvement.

**imp exact byte prefilter:** `https://github.com/kekzl/imp/commit/5ceb15ed1b0a70b2fab29fee3d9302ebdeb37dcf`. Inspected diff and `src/compute/schema_constrain_mask.cpp`. Probes256 first bytes and, when at most16 are legal, second bytes before expensive whole-token FSM simulation; caches plain-string flags. A rejected prefix cannot make a valid whole token. Author reports identical masks/per-token checks, CPU mask time10.85→0.52ms on a Qwen vocabulary schema walk, and server strictJSON85–88→96–98tok/s, unchanged unconstrained throughput. This fixes **imp's custom full-vocabulary simulation bottleneck**. Current NInfer uses XGrammar with a different precomputation/matching design; no equivalent speed gap established. Inspect exposed mask time before considering algorithm changes; the previously identified same-stream grammar dependency remains the more direct current-source lead.

**igorls branches:** `feat/device-sm-count` f52e209 queries actual active-device SM count instead of hardcoded170; author explicitly calls the PRO6000 result performance-neutral. Portability beyond the fixed5090 target is not a required feature. `d3-spec-trial` b871218 addresses Flash-Next MTP hidden norm and QSA NaN handling, not a27B speed technique. `feat/prefix-seed-store`5bb8e817 latest inspected commit merges partial tool-call recovery; no new durable-performance conclusion from its name alone. Qwen4-specific source would require a separate exact-artifact mathematical audit, not reuse by resemblance.

## SC07 — Independent MetaZenith fusion cross-check

Cross-reviewed `https://github.com/Intelligent-Internet/Qwen3.8-Inference-MetaZenith` source against this checkout for the ecosystem agent. `upstream/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:1273–1284` admits fused causal-convolution preparation only for pure prefill, no decode/spec partitions, head dimensions128 and compatible even head counts/dtypes. That is a relevant27B shape-specific lead.

Do not dismiss it merely because this repository has fused Q/K normalization: `src/ops/linear_attention/gated_delta_net/common.h:17–32` gates both current fused-normalization paths to **Hq=Hv=48**, the Qwen4 profile. Grouped Qwen3.8 **Hq16/Hv48** still materializes normalized Q/K; prefill `text_context_impl.h:1020–1041` separately launches causal convolution and GDN. Conversely, do not overstate Meta's memory elimination: its `causal_conv1d.py:448–650` preserves BF16 convolution rounding, stores raw Q/K to global output, executes a barrier, reloads for normalization and writes again. The fusion removes separate launch/layout/gating work but not every Q/K round trip. Its BF16 normalized output differs from local private FP16 normalization, so 'exact' relative to its own vLLM baseline does not establish this project's numerical criterion. Parent and ecosystem agent received these corrections before synthesis.
