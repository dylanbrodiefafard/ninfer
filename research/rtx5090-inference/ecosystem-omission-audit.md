## EO01 — MetaZenith / AutoResearch: materially relevant missing vLLM fork

Sources: https://github.com/Intelligent-Internet/Qwen3.8-Inference-MetaZenith ; https://github.com/Intelligent-Internet/Qwen3.8-Inference-MetaZenith/blob/main/benchmarks/profiles/r107-sm120.md ; https://github.com/Intelligent-Internet/Qwen3.8-Inference-MetaZenith/tree/main/benchmarks/results . **C+B.** README release commands use the alternate repository name `Qwen3.8-Inference-AutoResearch`; treat this as lineage/renaming, not two independent benchmark confirmations.

This is a vendored vLLM 0.27.1 optimization tree, not a deployment-only recipe. Exact target is RadixArk Qwen3.8-27B NVFP4, one 5090, TurboQuant4 KV, MTP3, C1/2/4. Profile fixes KV bytes 5,905,580,032, max batched tokens 12,480, long-prefill threshold 3,120, adaptive threshold, FULL_AND_PIECEWISE graphs and activation-quant fusion threshold 33. It says prefix caching was not explicitly enabled; that does **not** establish disabled caching when defaults can enable it.

The 18-cell pp2048/tg128 depth0–65,536 score is **client aggregate generation throughput including prefill**, geometric mean 51.9→84.9 (+63.5%). C1 depth0 99.3→185.5 and depth65,536 29→119 are not pure decode rates or comparisons to current NInfer. C4 depth65,536 remains 9.3→12.3. The 15-scenario one-trial deterministic tool gate is useful regression evidence, not proof of numerical identity or broad quality equivalence. README's early promise that benchmark docs will be added is stale relative to its later profile/log links.

Inspected concrete source:

- `upstream/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py:1275–1408` selects convolution directly producing normalized Q/K, V, g and beta for **pure prefill**, SiLU, Dk=Dv128, even local head counts, matching input/state dtype. Mixed/speculative work retains its existing route. `.../mamba/ops/causal_conv1d.py:778–819` allocates those output planes and passes pointers into the convolution kernel. This eliminates a separate intermediate convolution-output tensor and a separate postprocessing launch; it is not one monolithic convolution-plus-recurrence kernel. Independent local cross-review resolves the target-specific difference: NInfer projection/convolution fusion mainly covers small-token decode, while `text_context_impl.h:1020–1041` has separate prefill convolution. `src/ops/linear_attention/gated_delta_net/common.h:17–32` fused-Q/K-normalization predicates require Hq=Hv=48 (Qwen4); current27B Hq16/Hv48 still materializes normalized Q/K. Thus **prefill convolution→Q/K normalization/gates is a concrete missing27B fusion boundary**, fitting priority2. However source `causal_conv1d.py:448–650` preserves BF16 convolution rounding and stores raw Q/K, executes a debug barrier, then loads and normalizes them: this removes launches/layout passes, **not all global Q/K traffic**. Meta normalization outputsBF16 versus localFP16; upstream “exact” does not substitute for the local oracle criterion. No isolated local speedup is established.
- `upstream/csrc/libtorch_stable/turboquant_head_parallel_decode.cu` and `turboquant_shared_decode.cu` are actual specialized CUDA backends, not merely tuning flags. Head-parallel versus shared dequantized-KV schedules, context split policy, direct output and graph dispatch are useful comparative mechanisms. Their codebook/rotation ABI differs from NInfer NVFP4 KV; replacing the codec is not an exact drop-in optimization. Existing NInfer grouped-head/split attention also prevents calling reuse itself new.
- README composes activation quantization with GDN prefill; inspected convolution output planes remain ordinary Q/K/V and FP32 gates. Do not describe this as direct NVFP4 output from the recurrent GDN kernel without a specific further call-site proof. NVFP4 activation fusion is separately enabled by the recorded compiler pass.

**Disposition:** add to competitive source inventory and GDN-prefill producer/consumer investigation. It strengthens the fusion avenue; it does not overturn priorities using a 63.5% whole-stack uplift against old vLLM. This discovery falsifies a claim that all significant exact-model forks had already been covered.

## EO02 — vLLM Mach: persistent GDN fusion, with an unfavorable denominator trap

Sources: https://github.com/troycheng/vllm-mach ; https://github.com/troycheng/vllm-mach/blob/main/docs/gdn-decode.md ; https://github.com/troycheng/vllm-mach/blob/main/src/vllm_mach/mxfp6/gdn/gdn_fused_decode_sm120.cu . **C+B.** Current work is native MXFP6, not simply its historical EXL3 experiments. Validated setup is **two 5090s, TP2**, BF16 activations/KV, non-speculative text, C4–32. At C4 stock FP8 267.0, stock NVFP4 379.0, Mach default 377.2, full 384.9 aggregate tok/s: impressive FP8-relative headlines do not imply a large NVFP4-relative advantage. Full mode also combines FP16 state and approximate target-head shortlist/BF16 reranking; empirical top20 recall is not a certificate.

The CUDA source has an interesting narrower FP32-state route: BA GEMV + width4 convolution + gates/QK normalization + recurrence in one persistent launch. QKV projection remains separate; output norm/projection remain separate. A device-wide release/acquire barrier joins the GEMV/convolution producer phase to the recurrent phase; occupancy caps require all blocks resident, one in-flight call per scratch allocation. B1 prefetches SSM data before the barrier. M1/2/4/8 specialization exists. The isolated serving table reports 325.91→371.18 (+13.89%) C4, short single-run TP2 MXFP6; it is not a NInfer forecast.

Local `src/targets/qwen3_6_27b/impl/variant.cpp:497` already fuses RMSNorm+BA+gates; `src/targets/qwen3_6/impl/runtime/text_context_impl.h:904` then calls projection/convolution leaves and recurrence. Transplanting Mach breaks existing beneficial fusion boundaries and may introduce resident-grid constraints. **Disposition:** conditional alternative full-stage schedule, especially ordinary decode; not an additive microkernel or speculative-state implementation. Keep FP32 storage, exact state transactions and local performance classification. Historical Mach source-build versus stale FlashInfer JIT cache failure also cautions that patched source is not evidence the patched binary ran.

## EO03 — TRT-LLM current SM120 support and a reverted optimization

Sources: https://github.com/NVIDIA/TensorRT-LLM/pull/19376 ; https://github.com/NVIDIA/TensorRT-LLM/pull/18387 ; https://github.com/NVIDIA/TensorRT-LLM/pull/19578 . **C+B.** API status and actual patches inspected.

PR19376 merged September22 UTC, enables FlashInfer0.6.18 **prefill** on SM120/121. `_utils.py` separates prefill supported architectures90/100/103/120/121 from decode90/100/103; `gdn_mixer.py` uses the appropriate predicate. Author RTX PRO6000SE, Qwen3.5-4B FP8 TP1, 100 prompts ISL4K meanTTFT264.6→200.1ms (−24.4%). This supplies concrete support beyond stale hardware-list omission, but no exact27B5090 result. A generated review summary describing import-only changes is contradicted by the routing diff.

PR18387 merged September2 adds dense Qwen3.8 RadixArk/Inferact NVFP4 remapping/nested text-config LMhead loading, tested on PRO6000. This is artifact compatibility, not a measured steady-state kernel speedup. Mock architecture tests are not full-device benchmark validation.

PR19578 merged September24 **reverts** PR17365 direct indexed-state-pool GDN prefill on SM100/103. Adapter again gathers into packed state, executes, then scatters; preallocated workspace and the new SM120 prefill predicate remain. Underlying bug report is internal, so do not invent its cause. The reverted gather/scatter removal is not a currently admitted upstream optimization. This is a concrete falsification of treating every merged fusion PR as durable.

Historical https://github.com/JohnTDI-cpu/trtllm-nvfp4-blackwell-fix targets old v1.2rc4 MoE managed-weight handling and intentionally leaks raw cudaMalloc allocations; no native NInfer candidate. https://github.com/rdumasia303/tensorrt-llm_with_open-webui is a deployment recipe already covered. **Disposition:** strongest useful evidence is fused SM120 GDN prefill, already a high-ranked avenue; no new full-runtime migration recommendation.

## EO04 — ExLlamaV3 deeper release and unmerged backend audit

Sources: https://github.com/turboderp-org/exllamav3/releases/tag/v1.5.0 ; https://github.com/turboderp-org/exllamav3/pull/394 ; https://github.com/turboderp-org/exllamav3/pull/380 ; https://github.com/turboderp-org/exllamav3/pull/402 . **B+C for inspected PR patches.**

Release1.5.0 September13 reports Qwen3.8-27B EXL3 4bpw 5090 4Kprefill3766→4651 (+24%), ordinary S1decode78.54→78.58 (neutral). Release-wide prefill improvement is not attributed here to PR394, which remains **open**. Its multiple changes are not isolated in that table.

PR394 source `exllamav3_ext/attention_sm120_kernel.cuh` explicitly derives from llama.cpp FP16 SM120 attention: two-slot produced/consumed mbarriers, 3D TMA loads, warp-group synchronization and a D512 producerless refill variant. This is a lineage adaptation, not an independent invention of TMA attention. It implements native TMA paged prefill for CC12.0 with CUDA12.8+, compiled PTX/binary version checks, FP16 Q/K/V/cache, D128/256/512 and 256-token pages; min query33. Quantized KV, variable length, SWA, sinks and noncausal spans are excluded. D128 uses split1, D256/512 split1 or3, capped FP32 partial scratch256MiB. Author Windows11 RTX5090 CUDA13.3, Qwen3.8 EXL3 **6bpw FP16 KV**, chunk4096, three full-prefill plus128decode runs:16K3865→4020,32K3470.7→3678.8,65K2882.8→3231.6,100K2444.7→2853.9. KL versus Triton ~1.5e−5–3.5e−5 and token-agreement samples are reported. Useful alternative split/tile geometry, but wrong KV codec and existing NInfer TMA prefill prevent direct import or 16.7% forecast.

PR380 and402 are **closed, not merged**. PR380 superseded by334 records DFlash host-sampling synchronization and cropping acceptance losses: tau2.80 versus3.25 at8K in its 20-prompt test, and truncating the distribution can reduce acceptance. NInfer already device-samples; retain as a counterexample to universally beneficial crop/adaptive claims. PR402 stacks draft SWA ring work for MiMo on GB10; NInfer already owns a bounded DFlash window, and the named geometry is different.

- `FusedKVMaterializeHelper` stacks layer KV weights into **one torch.mm**, then a separate fused RMSNorm+RoPE Triton kernel, then pool writes. The header's “fused KV projection + RMSNorm + RoPE” is not a single fused GEMM epilogue. **Disposition:** useful concrete integration reference; no new priority above GDN prefill/TMA tuning from this evidence.

## Discovery method, unresolved experiment boundaries, and closure

Queries included RTX5090 TensorRT forks, EXL3 prefill/5090, ik NVFP4/DFlash, Kobold5090/context, HN5090 engines, explicit MAX/Fastllm names. GitHub updated issue/PR searches covered ik5090 (74 returned count), Kobold5090(13), EXL PRs(174), TRTsm120PRs(272), then relevant descriptions/diffs rather than pretending every result was code-reviewed. Counts describe query results, not audited-engine counts. Nondefault Pennyroyal tree and API PR status were checked explicitly. Followed primary source links and retrieved selective code/clones under `/tmp/ninfer-research/ecosystem`; no packages/models installed.

New high-value evidence has a concrete disposition: MetaZenith producer/consumer fusion joins the existing prefill investigation; Mach persistent fusion is a conditional alternate schedule; TRT status correction strengthens prefill while exposing a reverted indexed-state optimization; EXL paged TMA remains an unmerged alternate FP16 schedule. No exact end-to-end gain for NInfer is claimed. Local classifier/profiling/oracle experiments are future implementation admission work, not missing research measurements to fabricate. Search does not prove all public/private sources have been discovered.
