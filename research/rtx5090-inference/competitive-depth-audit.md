# Competitive depth audit: evidence that changes the first ranking

Retrieved 2026-09-26. This second pass was explicitly reopened after the user challenged the first pass's breadth. It includes newly discovered engine source, benchmark harnesses, current PR diffs and Radiance descendants. No external code was built or executed; no checkpoint was downloaded. C = implementation/diff inspected, M = author measurement, P = primary documentation, R = community discovery. Source IDs CD01–CD14 below are stable within this report.

## Revised decision

The first campaign's emphasis on copy proposals and PDL was too strong relative to its evidence. They remain bounded workload/schedule hypotheses, but should not lead a generic speed roadmap. Newly inspected negative evidence shows DFlash2 already exploiting repeated context and copy proposals displacing better neural proposals. A closer native competitor, SparkInfer, supplies actual SM120 schedules and a useful history of verification arithmetic failures. Exact-shape prefill/verify comparisons and serving-workload/companion alignment deserve higher evidential weight than generic launch overlap or more drafting strategies.

No newly inspected result is a matched performance lead over current NInfer. This is a conclusion about benchmark comparability, not evidence that NInfer is fastest. Important close competitors and contradictory results were missing from the first pass; this document corrects that coverage.

## CD01 — SparkInfer is a real omitted native comparator

Source: https://github.com/gittensor-ai-lab/sparkinfer ; snapshot `d27e913`, commit 2026-09-26T20:35:29Z. C/M/P. Relevant files: `README.md`, `CHANGELOG.md`, `kernels/csrc/cuda/fused/prefill_nvfp4_sm120.cu`, `runtime/src/models/qwen35_prefill.cpp`, `runtime/src/inference_engine.cpp`, `runtime/examples/dspark_tau_check.cpp`, `eval/pr_dspark_bot.py`, `bench/scripts/workloads.py`.

The current exact-family target is Gittensor's all-linear NVFP4 Qwen3.8-27B, not NInfer's Ostfralla shell. Its advertised +86% comparison is **Qwen3.6-35B-A3B MoE against llama.cpp**, not dense 27B. The current 27B bot table reports 95.7 tok/s ordinary decode and 6,942 prefill tok/s at context128, with 93.6/14,364 at4K. Its own mixed-precision Unsloth result is lower. This establishes a relevant engine to inspect, not an interchangeable arithmetic comparison.

The DSpark corpus table uses greedy C1, 128 output tokens, thinking disabled, best of3. It reports mean speedups over same-process AR of4.01×/2.97×/2.63× at4K/16K/32K. The hard16K prose gate is130.4 versus88.6 tok/s, acceptance1.730. `runtime/examples/dspark_tau_check.cpp:136–143` explicitly sets `int8_kv=false` and allocates two-byte KV elements: the gate harness is **BF16 KV**, not NInfer's default NVFP4 KV. The server's regular continuous-batch defaults and that harness must not be conflated. The release itself admits an earlier uncommitted corpus produced167.9 chat tok/s while the later committed corpus produced306.0 on the same engine. This falsifies treating a high short-output headline as a broadly transferable speed target.

Server DSpark eligibility is narrower than NInfer: greedy plain text, one active request, with autoregressive fallback for sampling, penalties, logprobs, media, or overlapping requests. `run_speculative` has explicit token publication and handoff to ordinary decode. A concurrency table from this engine does not establish concurrent DSpark capability. Exact greedy sequence checks are valuable for the qualified route but are not a theorem of stochastic law preservation or equivalence to BF16 source weights.

### Concrete kernel leads, not a wholesale engine port

`prefill_nvfp4_sm120.cu:35–129` implements a CUTLASS collective override that gives TMA B/scale loads an `EVICT_FIRST` cache hint while leaving A normal. This is distinct from ordinary `__ldcs` or access-policy windows: the hint is passed through the TMA copy object's third argument. Its documented workload has reused activation L2 traffic exceeding streaming weight traffic. Comments preserve a negative control (evicting A instead loses61%) and no gain from forcing A evict-last. Independent kernel-branch review confirmed `src/ops/linear/nvfp4/nvfp4_w4a4_tma.cuh:184–193` currently issues TMA without `L2::cache_hint`. NInfer has streaming hints and `cp_async_evict_first`, so the precise question is whether an admitted TMA prefill route has this same reuse conflict, not whether to add generic cache hints.

At lines171–211, the source keeps a `256×128×128` large-M tile and a transposed `128×16×256` small-row tile (M×N×K in kernel coordinates). The former's author comparison reports+6.7% at16K prefill against128×128×256; its instantiation also enables weight eviction, so this is a route result rather than an independently isolated tile-size effect. The transposed route swaps weights into M and activation rows into N and uses column-major output to retain the original output addresses, without requantization/repacking (`:648–678,1073–1074`). Shrinking that transposed N tile from64 to16 reduces waste and increases pipeline stages from3 to4. Reported cold M16 matrix times include down37.8→33.6 microseconds and output13.8→11.1. These are source comments, not independently reproduced measurements. NInfer already has shape-specific A16/W4A4 routes and efficient weight replay; only an exact geometry with classifier admission is a candidate. Do not assume an M16 route wins at C1 or W4/5.

`qwen35_prefill.cpp:5758` documents a real verification divergence from fused versus separate attention gating. Nearby code passes the true sequence-length hint to ensure verifier and ordinary decode select compatible scalar/tensor-core attention; passing−1 had silently selected the scalar path at all lengths. At6416 the faster packed head route is explicitly excluded from speculative verification because its reduction changes argmax relative to ordinary execution. These reinforce NInfer's numerical/acceptance qualification priorities. They do not require NInfer to copy SparkInfer's exact private reduction profile.

Disposition: promote SparkInfer to a primary **kernel and semantic comparison source**, especially prefill and verify dispatch. Its public server adds general JSON response grammar through XGrammar, corroborating the existing feature recommendation; importing its generic scheduler/model loader is outside this target's architecture.

## CD02 — LukasParke supplies contradictory drafting evidence, with reproducibility limits

Source: https://github.com/LukasParke/qwen38-27b-5090 ; snapshot `e6c9211`, 2026-08-25T15:20:16−05:00. C/M. Read `benchmarks/Benchmark-6.md`, `Benchmark-7.md`, `tools/bench_cascade.py`, production config and the MMVQ patch.

Headline211–293 single-stream and285 aggregate C4 are **IQ4_XS target + Q4_K_M DFlash2, f16 KV, a patched llama.cpp**, not NVFP4 execution. The main gain is forcing MMQ for multirow verification so weights are not re-streamed per row. That mechanism is substantially already addressed by NInfer's target weight replay. A24/25 greedy quality score against another GGUF is not exact artifact equality; “lossless” speculation also needs the particular sampler/verification implementation, not the label.

The August25 negative cascade matrix covers six fixtures: essay/code/math plus module renaming, table reformatting and changelog summarization. DFlash alone267.0 tok/s versus default ngram-first221.9 and tuned246.2. Even edit-code loses271.4→199.6/247.9. The author's explanation is specific: first-successful-proposer selection allows weak copy drafts to displace stronger DFlash proposals, increasing verification work for fewer accepted tokens. A later session-cache cascade loses33–64% on mixed examples. This is meaningful counterevidence to “copy-heavy means a free win,” not proof all copy proposers are bad.

Harness inspection supplies the actual workload contract: one server,131072 total context setting, target/draft GGUF, backend sampling, n7 (later n8), temperature1, top-k20, top-p0.95, at most384 output tokens, no prompt cache, thinking disabled. The reported mean averages backend per-request `predicted_per_second` **only for length-terminated fixtures**, rather than dividing all output by total wave time. No seeds are fixed. That differs from current NInfer's complete-wave benchmark.

There is also a concrete reproducibility defect: current `bench_cascade.py` defines per-configuration `cenv` entries for `SPEC_TAIL_N`/`SPEC_TRUNC_GAP`, prints them, but does **not** merge them into the environment passed to `start()`. Only MMVQ/PDL are forwarded. The checked-in CONFIGS now describe later F0–F4 arms rather than the original C0–C2 cascade arms. Therefore the file preserves fixtures and method but does not reproduce every reported experiment as checked in; treat the tables as author records. This defect does not prove that the original experiments were unrun.

The PDL “failure” is weaker: a single-pass n8 matrix gives269.9 for MMVQ1,272.0 for MMVQ2 and265.9 for PDL+MMVQ2. It has stochastic outputs, little repetition and a changed MMVQ setting, so supports **no demonstrated win**, not a categorical rejection of the different Wallawalla graph policy. Claimed drafter-oracle speed ceilings are corpus-dependent estimates, not hard physical limits for NInfer.

Disposition: copy/PDL should be lower-confidence, narrowly gated alternatives. Establish the actual missed work/acceptance opportunity before implementation. Existing strong DFlash performance is the relevant competitor to any copy proposal.

## CD08 — Murai-Labs: valuable failure records, overbroad causal language

Source: https://github.com/Murai-Labs/qwen3.8-27b-rtx5090 ; README and `bench/bench_fixed.py`, deployed recipe read. C/M/P. Single5090 WSL2, vLLM0.27.1, Unsloth mixed NVFP4/FP8, FP8 KV.200 fixed output tokens,3 repeats, cold nonce, median:51.5→107.6tok/s atp256 C1 withMTP3. C4 rows are per-request rates, not aggregate. The harness divides all completion tokens by first-to-last content-chunk time (including reasoning chunks); its separate aggregate rate uses full request-wave wall time. Nominal prompt sizes are generated by a four-characters/token heuristic, with actual token counts taken from usage, so `p256` is not guaranteed exactly256 input tokens. This is substantially different from both NInfer and the all-linear checkpoint recipes.

Its “never override KV dtype” warning is not a hardware law. The same report later narrows the evidence to TurboQuant+MTP failures in that version and identifies working quantized-KV counterexamples. Equal194/200 GSM8K outcomes and McNemarp1 do not prove token equality or universal losslessness. Its own section corrects an earlier template-causality claim: removing empty thinking blocks helps prompt hygiene, but did not fix observed context exhaustion. These are useful demonstrations of rejecting plausible explanations after controlled checks, not reasons to disable NInfer NVFP4KV or change its template.

## CD10 — Calney's original recipe: client/service cost and cache identity

Source: https://huggingface.co/calneymgp/Qwen3.8-27B-NVFP4-lmhead4-recipe . M/P; original card, not eemin mirror. Two useful observations: moving volatile fields behind~50K stable prefix reduced measured TTFT5.54→0.43s, and disabling LiteLLM detailed payload logging changed observed63K-context latency substantially. These are **prefix-hit and gateway measurements**, not CUDA engine speedups. A serving application can preserve stable serialized prefixes without NInfer rewriting user-message semantics.

The stated 8state slots/request belongs to its SGLang target+MTP buffer scheme, not universal GDN mathematics. NInfer already uses ReplaySSM/compact state. The card's1.94GB “8slots at~83MB” row is not arithmetically self-explanatory (8×83MB≈664MB), so no memory-saving estimate is derived from it. Its old “CuTeDSL unsupportedSM120” claim is superseded by current B12x code; specific recipes age faster than techniques. Alternating70K-prefix cache misses remain an author's unresolved cache-state problem, not evidence that NInfer lacks retention.

## CD11–CD13 — Radiance is a family, not just the first mirror

The first pass correctly identified AMD hardware but incompletely represented lineage. GitHub repository search `Radiance vllm in:name,description` returned12 repositories at retrieval. Six current descendant READMEs were inspected; original source is StillDeadcode on Codeberg, with `libr4d` as separate HIP kernels. No CUDA5090 Radiance implementation emerged.

- **CD11** https://github.com/Bjynt/vllm-radiance and https://github.com/magiccodingman/vllm-radiance preserve/extend StillDeadcode's R9700 stack. The latter explicitly keeps DFlash experimental because strict spec/non-spec greedy equivalence failed, and reports later GGZ14 residual-stream/norm fusion failed strict greedy/tool gates without speed benefit. This is stronger counterevidence than treating every Radiance fusion as qualified. Draft-only INT2 rerank and approximate **target** head pruning must stay separate.
- **CD12** https://github.com/SlyBase/vllm-sly-radiance has genuine additional single-R9700 work: widest gate/up projection had fallen onto wrong prefill path (step67→48ms); verify attention tuning and draft split-KV reportedly improved99K decode2.5×. These support exact shape/dispatch auditing, not a CUDA port. BF16 recurrent state, int4 head/embedding conversion and MXFP4 artifact changes do not preserve NInfer's target semantics by default.
- **CD13** https://github.com/Terrydaktal/vllm-coherence and https://github.com/drwolfen/radiance-vllm-qwen4exp . Coherence concentrates on preserving batch-dependent BF16/FP8 normalization arithmetic and continuation ownership; those are relevant verification failure patterns, not new native5090 math. The latter identifies itself as an R9V descendant of https://github.com/Dyluhn/R9V for dualR9700 Flash-Next with host expert streaming and approximate CED early exit. Different model, hardware and compute contract exclude direct adoption. https://github.com/drwolfen/radiance-vllm-r9700 is another tuned TP2 AMD deployment, not a distinct5090 engine.

## CD14 — The widely cited ratio-three GDN fallback is stale on current main

Sources: https://huggingface.co/Qwen/Qwen3.8-27B/discussions/51 ; https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/mamba/gdn/qwen_gdn_linear_attn.py . C/M/P. The August14 report correctly describes an old `num_v_heads == 8 * num_k_heads` guard excluding Qwen27B's ratio3. Its19.9→72.3tok/s comparison is **four5090s, TP4, BF16**, not the native single-card target.

Current source inspection falsifies using that report as a current bug: `_can_use_fused_gdn_mtp_decode()` explicitly accepts integral ratios `(1, 2, 3, 4, 8)`, with state-dtype, width and compiled-op checks. Passing the ratio check does not guarantee every deployment selects the fused route, but the particular old predicate is gone. This is independent of CD03's narrower packed ordinary-decode tile specialization.

## What is resolved and what remains conditional

This depth pass materially enlarges coverage and changes priority confidence. SparkInfer is now included; exact current PR diffs were inspected; Radiance descendants are distinguished; copy/PDL counterevidence and a harness defect are recorded; extra benchmark sources preserve their real denominators. The TMA/tile candidates were cross-reviewed by the kernel branch: the per-TMA hint is a real missing mechanism, but larger-M grids reuse B too, so unconditional evict-first is unjustified. That exact-shape admission, not another engine's headline, determines whether it deserves a future experiment. A final independent engine/mechanism search found KVarN (https://github.com/huawei-csl/KVarN), now screened in the kernel depth report: iterative variance normalization plus Hadamard K4V2, FP16 dense attention compute, TP2 Qwen3-32B showcase and no matched5090 evidence. It adds a quality/capacity comparator, not a new native decode priority.

Unreproduced results remain author measurements. The inaccessible New Guard detailed report is a named evidence limit. No claim of a current NInfer speedup or exhaustive Internet completeness follows from this report.
