## FD-02: igorls/ninfer — concrete general structured-output implementation

Source: https://github.com/igorls/ninfer ; inspected87812bc. Specific diff: https://github.com/igorls/ninfer/commit/2cbdb2b6c8edcfbb6f57533e4e3ef12def7edfbf . This is a fork with broader RTX PRO6000/Windows/checkpoint interests, not an independently matched5090 benchmark.

Unlike current NInfer's tool-argument grammar, this fork accepts Chat `response_format` and Responses `text.format` JSON object/schema modes. Code anchors: `src/serve/request_validation.cpp:16–57`, `openai_chat_request.cpp:927`, `openai_responses_request.cpp:967`; `src/runtime/contract/structured_output.cpp` validates a supported keyword subset, rejects unsupported constraints, compiles schema, and owns request matchers. It does **not** promise arbitrary JSON Schema support.

Commit2cbdb2b removes the blanket zero-MTP extent for constrained output. It forks the request grammar matcher along host-known drafts, truncates at rejection/completion, and supplies a separate allowed-token mask for every verification column (`allowed_tokens_column_stride`; `src/targets/qwen3_6/impl/runtime/program_impl.h`, `src/ops/kernel/speculative_round.cuh`). DFlash2 remains zero extent because its proposal is produced inside the round. Author measurement: greedy JSON output79–89tok/s versus34–35, token-identical to nonspeculative constrained output, RTX PRO6000 with another serving instance active. That is useful implementation evidence and a heavily scoped claim, **not** a5090 speedup or stochastic qualification.

Actionable difference: design the general-output contract and reuse existing current grammar transactions, informed by this fork's endpoint validation and per-column mask handling. Current tool grammar already supports speculative target positions; do not replace it with a blanket grammar feature claim. Qualify schema termination, grammar/state rollback, current p-less sampling and DFlash separately. The inspected fork has an Apache-2.0 LICENSE; retain relevant notices if extracting code. No code copied during research.

## FD-03: knoopx/ninfer — branch decisions rather than generated explanations

Source https://github.com/knoopx/ninfer ; inspected5278687, Apache-2.0 LICENSE. Feature commit https://github.com/knoopx/ninfer/commit/bf84a4f72fc23b18d3f66e916e5fc32de1bbc8ff . Source-level diff reviewed (68 files), not executed.

Adds public `Engine::prepare_decision/decision_score`, candidate label projections and `candidate_slice_softmax` Op, resident-state branch transactions, and `POST /v1/decisions`. `docs/decisions.md` defines zero output tokens, a shared state prefix, per-question suffixes, probabilities normalized over the selected label set, and serialization with generation through the execution lock. Paths: `include/ninfer/decision.h`, `src/runtime/engine/decision_score_core.h`, `src/models/qwen3_5/program/transactions/decision_branches.cpp`, `src/ops/kernel/candidate_slice_softmax.cuh`. Commit75ef955 sizes workspace to live branch count rather than every configured branch.

Potentially useful for local classification/routing/scoring without token generation and repeated shared-prefix prefill. This is a **new product feature**, not a faster implementation of normal generation. Candidate-conditioned softmax is not calibrated task accuracy or an unconditional vocabulary probability. Branch count and scheduling must fit currentC1..4 ownership; fork router/model TTL is outside current single-resident scope. Its PDL commitac219fb shares the already reviewed policy lineage, so must not be counted as independent corroboration. Its advisory required/strict tool-choice handling must not be confused with strict enforcement.

## FD-04: Quasar/q27 — directly relevant overlooked native engine, with corrected comparisons

Source https://github.com/signalnine/q27 ; inspected8be624e native `src/` and README. This **Quasar engine** is unrelated to the QUASAR-QAT quantization project. C/CUDA Qwen3.6/3.8 dense27B, custom q4s/q5f and additional ternary profiles; these are not the current `.ninfer` NVFP4 artifact. MIT license in repository.

Real incremental ideas: host suffix-match drafter `src/suffixdraft.h`, multi-width shared-weight verification (`src/vgemm.cuh`, `src/fdmma.cuh`), and staged recurrent-state commit in `src/spec3.cuh`. The suffix proposer searches the committed prompt/output stream; it does not alter target weights. `src/sampling.h:329–373` implements deterministic-proposal acceptance against the served distribution and exclusion of the rejected token from residual sampling; the same file explicitly distinguishes greedy equality. `src/spec3.cu:1408` comments that in-grammar rounds accept only the pending token. Thus an interesting copy-draft reference, but not proof that wide speculation remains enabled under every grammar mode. Current recurrent transaction and stochastic correctness must be independently qualified, as for Wallawalla.

The README is unusually informative about **negative comparison corrections**. Older SWE-bench wall-time advantages shrink after NInfer prefix reuse fixes; a later DFlash2 NInfer run wins a workload whose output/turn counts differ. q27 then finds a tokenizer defect that emitted tool-added-token spellings as text; fixing it reduces excessive thinking substantially. Headline rates from those revisions should not be treated as an engine ranking. Its later similar approximately220 versus218tok/s DFlash2 rates remain old workload claims, not current checkout evidence. These disclosures strongly support fixed prompt/template/tokenizer/cache conditions and task completion time alongside tokens/s.

Additional custom quantization/prefix-normalization/ternary claims require artifact and semantic review. Changing billing-header text to obtain prefix matches would be an input-semantic change, not free cache optimization. Bonsai weight changes and different answer lengths cannot establish same-artifact NVFP4 gains. Disposition: high-value reference for copy-draft/verification design, no current speed winner established.

## FD-05: Paddock and PegaInfer are independent engines, not missing wrappers

**Paddock:** https://github.com/truespar/paddock ; inspected610cd8f, native Rust orchestration plus CUDA pack. Dual MIT/Apache2. Native quantized paths, paged state and speculative verification exist in `packs/cuda/src/`; this is distinct from unrelated Apple-oriented projects named Paddock. The advertised benchmark board includes Qwen3.8-27B FP8 on **RTX PRO6000**, speculation disabled; its C32 throughput or ratios to vLLM/SGLang are not the5090 NVFP4 C1..4 contract. Tested5090 support is not a matched performance result.

Useful code-level negative result: `packs/cuda/src/attn/prefill_fa2.cuh:14–47` records a failed FA2 restructure: at its2048-row tick, HD256 variant1011µs vs943 and HD5126743vs5124. It attributes loss to phase-chain latency/co-residency and redundant KV walks despite fewer instructions. The same source records beneficial padding and compile-time geometry experiments in that lineage, but these are developer comments rather than independently reproduced evidence. Paddock's incumbent may use FP16 accumulation whereas candidate FP32 changes arithmetic; its greedy probes are not the independent mathematical Op oracle required here. Disposition: inspect shape-specific co-residency and padding if local profiling identifies the matching bottleneck; no generic 'replace attention with FA2' recommendation.

**PegaInfer:** https://github.com/pegainfer-project/pegainfer ; inspectedb2efe52, Apache-2.0 LICENSE; first-party background https://pegainfer.org/blog/pegainfer-010/ . Rust engine with model-owned runtimes, native CUDA plus external FlashInfer/Triton paths, not just a launcher. Repository README Qwen3-4B BF16 RTX5090 footprint at70888b2 versus vLLM0.24.0 reports771MB versus3814MB host resident memory and about3s startup versus32.7s warmed-compile vLLM. This does not beat an already AOT NInfer27B path. Qwen3.5 support is text-only BF16, so27B capacity/identity differs.

The stronger new lead is `docs/models/qwen3/dspark-integration.md`, `pegainfer-qwen3/src/dspark.rs`: a DSpark rank256 sequential Markov head added to DFlash proposals, reusing verify/KV machinery, claims **+3.6% geometric-mean outputtok/s** on a5090 greedy sweep versus matched block7 DFlash, accepted drafts2.52vs2.30. This requires the specific **Qwen3-4B DSpark checkpoint**; it cannot be transplanted as trained weights for27B. The report distinguishes anchor-first versus anchor-drop checkpoint semantics and records correction of a bug that wrongly tied anchor behavior to presence of a Markov head. Phase1 parsed but did not use the confidence head, so citing the scheduler paper as implemented here would be false. Parent kernel/speculation investigation received this lead for independent examination. Disposition: trained-drafter future avenue with exact artifact prerequisite; current loader/graph design inspiration only.

## FD-07: sergiuszm/ninfer-5090 — causal interior specialization, limited novelty
